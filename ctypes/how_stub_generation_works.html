The bindings module

The goal of this document is to explain what goes on behind the scenes when using stub generation, in particular in the tutorial.

The most "interesting" part that we wrote is the module that describes our bindings. It corresponds to the module type Cstubs.BINDINGS. In the tutorial, that Bindings.Generate (Cstubs.BINDINGS is a functor type, so Bindings.Generate has an argument).

Stub generation

When generator.exe is executed, this module is passed as an argument to Cstubs.write_ml and Cstubs.write_c.

Let's see in detail how this part works. Cstubs.BINDINGS is the type of a functor with input Ctypes.FOREIGN and an empty output signature. This means that all the interesting work is done as a side effect when the functor is applied.

Ctypes.FOREIGN is a DSL that represents C types and declarations. Given the description of some C values in that format, it is possible to write some printers that will output this description in OCaml and C formats. This is what Cstubs.write_ml and Cstubs.write_c do: they output the OCaml and C sides of a C library that exposes the values.

Let's see how it works in the context of our tutorial.

First, a C name is generated for each C function to bind. For example, the C function double tgamma(double) will be wrapped into a C function value gamma_1_tgamma(value).

Then, the C part generates a C function that wraps the function with the right macro calls:

value gamma_1_tgamma(value x1)
{
   double x2 = Double_val(x1);
   double x5 = tgamma(x2);
   return caml_copy_double(x5);
}

Finally, the OCaml part defines an external function that corresponds to that generated C function:

external gamma_1_tgamma : float -> float = "gamma_1_tgamma"

The generated OCaml part contains more code, but let's leave it here for now.

Linking

This generated OCaml code is linked with the generated C code into a library (named generated in the tutorial).

To summarize, so far:

  • we wrote a bindings library
  • bindings has been used by ctypes to create a generated library

One last functor application

This is where things get really interesting.

Notice that there are two loose threads here:

  • in generated, we've defined a gamma_1_tgamma OCaml function, but the consumer of the library can not know about this generated name.
  • in bindings, we've defined some OCaml names for the result of the foreign call, but never used these for now.

Actually, these are related. In the stub generation step before, Cstubs.write_ml actually generated glue code so that the Generated module conforms to the Ctypes.FOREIGN module type.

In particular, this glue code ensures that foreign "gamma" will call gamma_1_tgamma.

Since Generated has the right module type, this explains that the contents of gamma.ml in the tutorial is just:

include Bindings.Generate(Generated)

It includes a tgamma : float -> float function, and users of the library can call it.

At runtime

Finally, let's see what happens when a Gamma.tgamma 4. is evaluated.

The definition of Gamma.tgamma comes from the body of Bindings.Generate(Generated). In other words, it is:

open Ctypes
open F

let tgamma = foreign "tgamma" (double @-> returning double)

Here, F is instanciated as Generated. So the definition of foreign is:

let foreign : type a b. string -> (a -> b) fn -> (a -> b) =
  fun name t -> match t, name with
| Function (CI.Primitive CI.Double, Returns (CI.Primitive CI.Double)),
  "tgamma" -> gamma_1_tgamma
(* ... *)

This pattern matching happens at module load time and simplifies to:

let tgamma = gamma_1_tgamma

This function is defined in the same Generated module as:

external gamma_1_tgamma : float -> float = "gamma_1_tgamma"

So, tgamma 4. passes 4. to the C function gamma_1_tgamma.

It is available in the linked generated stubs:

value gamma_1_tgamma(value x1)
{
   double x2 = Double_val(x1);
   double x5 = tgamma(x2);
   return caml_copy_double(x5);
}

Values of type float are passed boxed to the OCaml runtime (this value is a pointer). Double_val returns the underlying double (x2 is 4.). The actual function from the libc is called and the result is stored in x5 (m \Gamma(4) = 6 so x5 is 6.). Finally, this result is returned boxed to the OCaml runtime (caml_copy_double allocated a block with Double_tag and stores the 6. value in it).

Execution resumes on the OCaml side, and the return value is propagated to the call site of Gamma.tgamma 4..
